## 何をする道具か

Claude Code は、ターミナルで動くコーディングエージェントです。リポジトリを読み、ファイルを編集し、コマンドを実行し、テストを回して結果を見て直す、を自分で繰り返します。「コードを書いてもらう」より「作業を任せて確認する」道具です。

このアプリ自体も、レッスンの執筆・ビルド・テスト・デプロイの大半をこの形で進めています。

## 最初の設定: CLAUDE.md

リポジトリ直下の `CLAUDE.md` は、毎回読み込まれるプロジェクトの説明書です。人間の新メンバーに渡す README の「作業の作法」部分を書きます。

```markdown
# study-quiz

学習アプリ。content/ の md + yaml が正、scripts/build.py で site/ を生成。

## コマンド
- ビルド: uv run python scripts/build.py
- テスト: uv run pytest -q
- lint: uv run ruff check .

## 作法
- 問題は必ずレッスンに属する (隣の yaml の lesson: が md の id と一致)
- yaml の question / choices / explanation は必ずダブルクォートで囲む
- 公開リポジトリなので社内情報・プロジェクト名を書かない
- push 前に build → pytest → ruff を通す
```

- **短く、具体的に**。長い文書は読まれても効きが薄い
- 「何を」より「どう判断するか」(禁止事項、優先順位)
- 詳細は `docs/` に置き、CLAUDE.md からはパスを指す
- `~/.claude/CLAUDE.md` に個人の好み (言語、口調) を置ける

## 権限

既定では、ファイル編集やコマンド実行のたびに確認が入ります。

- 安全なコマンド (`uv run pytest`、`git status`) は許可リストに入れて毎回聞かせない
- 破壊的なもの (`rm -rf`、`git push --force`、本番への操作) は聞かせる
- 設定は `.claude/settings.json` (リポジトリ) と `~/.claude/settings.json` (個人)

「全部許可」にすると速いですが、本番の秘密や force push が絡む場所では危険です。信頼の境界を自分で決めます。

## スキル (SKILL.md)

繰り返す手順を、再利用できる指示書にします。`.claude/skills/<name>/SKILL.md`。

```markdown
---
name: add-lesson
description: 新しいレッスン (md + yaml) を追加し、ビルドとテストを通す
---
1. content/<category>/NN-slug.md と 同名 .yaml を作る (既存の 01-*.md の形に倣う)
2. yaml の lesson: を md の id と一致させる。値はダブルクォート
3. 本文末尾に「## やってみる」節、確認問題は 4 問以上
4. categories.yaml の planned から該当行を消す
5. uv run python scripts/build.py && uv run pytest -q && uv run ruff check .
6. 社内名が無いか grep で確認してからコミット
```

- `/add-lesson` のように呼び出せる。「毎回同じ説明をしている」と気づいたらスキルにする
- `description` は「いつ使うか」が分かるように。エージェントが自動で選ぶ手がかりになる
- 手順書と同じで、コマンドは具体的に、判断基準は明文化

## フック

ツール実行の前後に自動で走らせる処理です (`settings.json` の `hooks`)。

- ファイル編集後に自動で `ruff format` を掛ける
- `git push` の前にテストを強制する
- 危険なコマンドをブロックする

「エージェントに毎回お願いする」のではなく「機械的に必ず起きる」にしたいものはフックにします。

## 良い頼み方

| 悪い | 良い |
|---|---|
| 「API 作って」 | 「POST /attempts を追加。body は question_id と result。attempts に INSERT し review_schedule を UPSERT。テストも」 |
| 「直して」 | 「pytest のこのエラーを直して。原因を先に説明して」 |
| 「いい感じに」 | 「既存の routers/actors.py の形に合わせて」 |

- **完成条件** を言う (テストが通る、curl でこう返る)
- **参照先** を示す (この既存コードに倣う)
- **やらないこと** も言う (DB スキーマは変えない)
- 大きい作業は計画を先に出させ、確認してから実行させる
- 結果は必ず自分で読む。テストの出力、差分。「通った」と言われても `git diff` を見る

## 使いどころ

- 向く: 定型の実装、テストの追加、既存コードの読解と説明、リファクタリング、調査 (「この関数はどこから呼ばれる?」)、ドキュメント
- 向かない / 慎重に: 要件が曖昧な設計判断、本番データに触る操作、セキュリティの最終判断。判断はこちらが持つ

## まとめ

- CLAUDE.md に作法を短く。判断基準と禁止事項
- 権限は安全なものを許可、破壊的なものは確認
- 繰り返す手順はスキル、必ず起きてほしいことはフック
- 頼むときは完成条件・参照先・やらないこと。結果は自分で読む

## やってみる

**ゴール:** CLAUDE.md とスキルを 1 つ作り、エージェントに定型作業を任せて差分を読む。

1. 自分のリポジトリに `CLAUDE.md` を書く: コマンド 3 つ (テスト / lint / 起動) と作法 3 つ (禁止事項を含む)
2. `.claude/skills/run-checks/SKILL.md` を作る: 「lint → テスト → 失敗があれば原因と修正案を報告、修正はしない」という手順
3. Claude Code を起動し `/run-checks` を実行。報告の形式が指示どおりか見る
4. 「`tests/test_x.py` に境界値のテストを 3 つ足して。既存のテストの書き方に合わせて。本体は変えないで」と頼み、`git diff` を読んでから受け入れるか決める
5. `.claude/settings.json` に安全なコマンド (`uv run pytest`) の許可を足し、確認が減るのを見る

**確認:** スキルで定型作業が 1 コマンドになった。出てきた差分を自分で読んで判断した。
