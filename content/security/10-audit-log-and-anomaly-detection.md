## 目的

「攻撃されているか」「内部の誰かが不正をしていないか」に **気づく** ことです。防御は破られる前提で、破られたときに早く知り、後から説明できる状態を作ります。設計のレッスンの「イベントと監査ログ」が構造の話なら、ここは運用の話です。

## 記録する対象

| 種類 | 例 | 取り方 |
|---|---|---|
| 認証 | ログイン成功 / 失敗、パスワード変更、MFA の有効 / 無効、トークン発行 | アプリの認証コードで明示的に |
| 権限 | ロール変更、管理者の追加、API キー発行、共有設定の変更 | アプリ + IAM の監査ログ (CloudTrail / Cloud Audit Logs) |
| データ | 個人情報の閲覧・エクスポート、削除、一括更新 | アプリで明示的に (読み取りも) |
| 設定 | 環境変数 / Secret の変更、デプロイ、ファイアウォールの変更 | クラウドの監査ログ、CI の履歴 |
| インフラ | SSH / SSM のセッション、DB への直接接続 | SSM ログ、DB の接続ログ |

各レコードには **誰が (actor)、いつ、何に (subject)、何を (action)、どこから (IP / UA / request_id)、結果** を入れます。

## 改ざんできない置き場

監査ログをアプリの DB の普通のテーブルに置くと、侵害されたときに消されます。

- DB に置くなら、アプリのロールには **INSERT のみ** (UPDATE / DELETE 不可)。owner ロールは分離
- 加えて **外部へ流す**: Cloud Logging / CloudWatch Logs のシンク → 保持ポリシー付きバケット (GCS Bucket Lock、S3 Object Lock)。書いた本人も消せない
- 保持期間は業務・法令で決める (1〜7 年)。アプリログより長い
- クラウドの監査ログ (Cloud Audit Logs、CloudTrail) は既定で有効。**組織レベル** で集約バケットに流し、プロジェクト管理者が消せないようにする

## 検知するパターン

| パターン | 検知の条件 (例) |
|---|---|
| 総当たり | 同一 IP or アカウントで 10 分に 20 回のログイン失敗 |
| クレデンシャルスタッフィング | 多数のアカウントに対し各 1〜2 回の失敗が短時間に |
| 不可能な移動 | 同一アカウントが 1 時間以内に日本と欧州からログイン |
| 権限昇格 | 管理者ロールの付与、IAM ポリシー変更 (人が意図したか都度確認) |
| 大量取得 | 1 ユーザーが通常の 10 倍のレコードを取得 / エクスポート |
| 深夜の管理操作 | 業務時間外の削除・設定変更 |
| 新しい鍵 | サービスアカウント鍵 / アクセスキーの作成 (作らない運用なら即異常) |
| 公開設定 | バケットや DB がパブリックに変わった |

最初は上の 3〜4 個 (総当たり、権限昇格、鍵作成、公開設定) をアラートにし、残りはダッシュボードで眺めるところから。

## 実装の型

```
アプリ ──構造化ログ (severity, event, actor, ip)──▶ Cloud Logging / CloudWatch
                                                       ├─▶ ログベースメトリクス → アラート (閾値)
                                                       ├─▶ シンク → 保持付きバケット (長期保存、改ざん不可)
                                                       └─▶ BigQuery / Athena (相関、調査)
```

```python
audit.info("auth.login_failed", extra={"extra_fields": {"email_hash": h(email), "ip": ip, "ua": ua, "request_id": rid}})
```

- メールアドレスそのものではなくハッシュ (ログに個人情報を残さない)。調査時は既知の値をハッシュして照合
- クラウド側は Security Command Center (GCP) / GuardDuty (AWS) を有効にすると、鍵作成・公開設定・異常な API 呼び出しを既定で検知する。まずこれを ON

## アラートが鳴ったら

1. 影響範囲: どのアカウント、何にアクセスされたか (監査ログで追う)
2. **封じ込め**: パスワード / トークン / 鍵の失効、アカウントの一時停止、IP のブロック
3. 証拠の保全: ログをエクスポート。消さない、上書きしない
4. 復旧と原因: どこから入ったか (脆弱性、漏れた鍵、フィッシング)
5. 振り返りと再発防止 (SLO のレッスンの型)

「誤検知だった」も記録し、閾値を調整します。

## 定期的に見るもの (月次)

- ログイン失敗の推移、429 の件数
- 権限変更の一覧 (誰が誰に何を)。意図しないものが無いか
- 作られた鍵 / アクセスキー、90 日以上使われていない認証情報
- 公開されているリソース (Access Analyzer / SCC の検出)
- 監査ログのシンクが動いているか (止まっていたら「記録が無い」になる)

## まとめ

- 認証・権限・データ・設定・インフラの操作を、誰が・いつ・何を・どこから、で記録
- INSERT のみ + 外部の保持付きバケット。組織レベルで集約
- 総当たり・権限昇格・鍵作成・公開設定から検知を始める。SCC / GuardDuty を ON
- 鳴ったら封じ込め → 保全 → 原因 → 再発防止

## やってみる

**ゴール:** ログイン失敗の監査ログを出し、閾値でアラートを作り、鳴らす。

1. be-10 の FastAPI のログイン失敗で、`auth.login_failed` を構造化ログ (py-10 の JSON) で `email_hash`、`ip` 付きに出す
2. ローカル: `for i in $(seq 25); do curl -s -X POST localhost:8000/auth/login -d 'username=a@x&password=wrong'; done` で 25 行出るのを見て、`jq 'select(.message=="auth.login_failed")' | wc -l` で数える
3. Cloud Run にデプロイしているなら、Cloud Logging で `jsonPayload.message="auth.login_failed"` のログベースメトリクスを作り、「5 分で 20 件超」のアラートを作って上のループで鳴らす
4. GCP: Security Command Center の Standard を有効化 (無料) し、検出結果を見る。AWS なら GuardDuty の 30 日無料トライアル
5. 監査ログ用のバケットを作り、保持ポリシー (1 年、ロック) を設定してみる (削除できなくなるのでテスト用の短い期間で)

**確認:** 失敗ログがフィールド付きで出て、閾値で通知が来た。消せないバケットの設定を見た。
