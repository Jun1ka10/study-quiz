## 設計の目的

設計とは「あとで変更しやすいように、コードをどう分けてどうつなぐかを決めること」です。動くだけならどう書いても動きます。差が出るのは、仕様変更が来たときです。

- 変更が 1 か所で済むか、あちこちに散るか
- 直したときに別の場所が壊れないか
- 読んだ人が意図を理解できるか

これを支えるのが **凝集** と **結合** という 2 つの物差しです。

## 凝集 (cohesion): 中身のまとまり

1 つのモジュール (関数・クラス・ファイル) の中身が、1 つの目的のために集まっているほど「高凝集」です。

```python
# 低凝集: 関係ないことが同居している
class Utils:
    def send_mail(self, ...): ...
    def calc_tax(self, ...): ...
    def parse_csv(self, ...): ...
```

メール送信の仕様変更でも、税率の変更でも、同じクラスを触ることになります。変更理由が複数あるのは低凝集のサインです。

## 結合 (coupling): 外との依存

モジュール同士がどれだけ互いの中身を知っているか。少ないほど「疎結合」です。

```python
# 密結合: 注文処理が DB の細かい実装を直接知っている
def place_order(order):
    conn = psycopg2.connect(DSN)
    conn.execute("INSERT INTO orders ...")
    smtplib.SMTP("mail.example.com").send(...)
```

DB を変えたい、メールを Slack にしたい、テストしたい、どれも `place_order` を書き換えることになります。

```python
# 疎結合: 「保存する」「通知する」を外から渡す
def place_order(order, repo, notifier):
    repo.save(order)
    notifier.notify(order)
```

こうすると `place_order` は保存先や通知手段を知らず、テストでは偽物を渡せます。

## 目指す形

**高凝集・疎結合**。関係あるものは一か所に集め、外への依存は細い口にまとめる。この後のレッスンで出てくる SOLID もレイヤーも DDD も、すべてこの 2 つを実現するための道具です。

## まとめ

- 良い設計 = 変更しやすい
- 凝集: モジュール内のまとまり。変更理由が 1 つになるように
- 結合: モジュール間の依存。変更が連鎖しないように
