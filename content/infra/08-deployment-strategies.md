## 目標

デプロイは「壊れたらすぐ戻せる」「ユーザーに止まって見えない」の 2 つを満たします。速さより **戻せること** が先です。

## 方式

| 方式 | 動き | 長所 | 短所 |
|---|---|---|---|
| 再作成 | 全部止めて入れ替え | 単純 | 停止時間がある |
| ローリング | 1 台ずつ (1 インスタンスずつ) 新版に置き換え | 無停止、追加資源が少ない | 新旧が同時に存在する時間がある |
| ブルーグリーン | 新版を丸ごと別に立て、LB を切り替え | 切り戻しが一瞬 | 資源が 2 倍 |
| カナリア | 新版に 5% だけ流し、問題なければ広げる | 影響を小さく本番で検証 | 監視と振り分けの仕組みが要る |

Cloud Run は既定でローリング (新リビジョンが起動したら切り替え) で、トラフィック分割でカナリアもできます。ALB + Auto Scaling も同様。VM 1 台の Django なら「新版を別ディレクトリに展開して gunicorn を graceful reload」が最小のローリングです。

## 新旧が同時に存在する

ローリングとカナリアでは、旧版と新版が **同時に** リクエストを受けます。ここで壊れやすいのが DB と API の互換性です。

### DB マイグレーションは「展開 → 契約」の 2 段階

列の改名を 1 回でやると、旧版が古い列名で落ちます。

```
1. 展開 (expand):  新しい列を追加。旧版はそれを無視して動く。新版は両方に書く (または新列を読む)
2. デプロイ:       新版に切り替え
3. 契約 (contract): 全部新版になってから、古い列を削除する (別のリリースで)
```

- 追加は安全、削除と改名は 2 段階
- `NOT NULL` の列追加は、まず NULL 許可で追加 → 埋める → NOT NULL にする
- 大きいテーブルのインデックス作成は `CONCURRENTLY`。ロックで止まる

### API も同じ

新しいフロントが古い API を呼ぶ、古いフロント (ブラウザに残っている) が新しい API を呼ぶ、が起きます。API 設計のレッスンの「壊さない変更」を守れば耐えられます。

## ロールバック

「戻す」を **先に** 用意します。

- イメージは commit SHA でタグ付けし、前のタグに戻すだけでロールバックできる (Cloud Run なら前のリビジョンにトラフィックを戻す)
- DB は戻せない前提で、展開 → 契約にする (旧版が新しいスキーマでも動く)
- 設定 (環境変数、Secret のバージョン) も一緒に戻る形にする。コードだけ戻して設定が新しい、で壊れる
- 戻す手順を README ではなく **コマンド 1 つ** (workflow_dispatch や Makefile) にする

「本番で 5xx が増えた → 5 分以内に前のリビジョンへ」を練習しておきます。

## フィーチャーフラグ

コードは出すが機能は隠す。

```python
if settings.flags.new_review_algo:
    due = next_due_v2(...)
else:
    due = next_due(...)
```

- 大きい機能を小さな PR で順に入れられる (未完成でも main に入れる)
- 特定ユーザーだけに出して検証 (カナリアの機能版)
- 問題が出たらデプロイ無しで OFF
- フラグは **消す**。役目を終えたフラグが残ると分岐が積もる

環境変数か設定テーブルで持ち、最初は環境変数で十分です。

## ヘルスチェックと起動の作法

- `/healthz` は軽く (プロセスが生きているか)。`/readyz` は依存 (DB) まで見て「受け付けてよいか」
- 新版は readyz が通るまでトラフィックを受けない。起動に時間がかかるアプリでは特に
- 停止は **graceful**: SIGTERM を受けたら新規受付を止め、処理中を終えてから終了。gunicorn / uvicorn は対応している。Cloud Run は 10 秒程度の猶予

## デプロイの前後でやること

前:

- CI 緑、マイグレーションの plan (何が変わるか) を読む
- ロールバック手順が使えることを確認
- 時間帯 (トラフィックが少ない、人がいる)

後:

- エラー率・レイテンシ・ログを 10〜15 分見る (デプロイ直後のアラートを見逃さない)
- 主要な導線を 1 回手で触る
- 「デプロイした」を記録 (誰が、何を、いつ)。障害調査の起点になる

## まとめ

- 戻せることが先。イメージはタグ、前のリビジョンへ 1 コマンド
- 新旧が同時に存在する。DB は展開 → 契約、API は壊さない変更
- 大きい機能はフラグで隠して小さく出す。フラグは消す
- readyz と graceful 停止。デプロイ後 15 分は見る

## やってみる

**ゴール:** Cloud Run (無ければ compose) でカナリアとロールバックを体験する。

1. gcp-02 の demo サービスの `/healthz` の応答に `"version": "v1"` を入れてデプロイ (`--tag v1` でリビジョンにタグ)
2. `"v2"` に変えてデプロイするとき `--no-traffic` で流さず、`gcloud run services update-traffic demo --to-revisions <v2 リビジョン>=10,<v1>=90` で 10% だけ流す
3. `for i in $(seq 20); do curl -s URL/healthz; echo; done` で v1 と v2 が混ざるのを見る
4. `update-traffic --to-revisions <v1>=100` で一瞬で戻す (ロールバック)
5. 展開 → 契約を SQL で: be-08 の PostgreSQL で `alter table users add column display_name text;` → アプリが両方に書く想定 → `alter table users drop column email;` は「全部新版になってから」と手順書に書く
6. Cloud Run が無ければ compose で `api` を 2 サービス (`api-v1`, `api-v2`) 立て、nginx の upstream 重みで振り分ける

**確認:** 新旧が同時に動く状態を見た。1 コマンドで戻せた。
